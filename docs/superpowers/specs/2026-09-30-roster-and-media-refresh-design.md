# Roster Trim and Media Refresh — Spec

**Sources:** `تعديلات مهمة .pdf` (client media brief, 2 pages, 27 embedded Drive
links) plus a roster list supplied in chat. Both received 2026-09-28.
**Status:** scoped and approved for planning.

Two requests arrived together and are treated as one piece of work because the
second cannot ship without the first's groundwork:

1. **The roster** — drop four clients, reorder the rest into a named sequence.
2. **The media brief** — replace the design and video material for fourteen
   clients from Google Drive folders the client supplied.

They are sequenced behind a third piece of work neither request mentions but
both depend on: the current design exists only in the generated embed, so the
build that the media pipeline ends with would erase it.

---

## Why the port comes first

`beeviro-embed.html` is generated by `build-embed.mjs` from `site/`. It has been
hand-edited across several sessions and now carries five features that have no
source in `site/` at all:

| feature | references in embed | in `site/` |
|---|---|---|
| services section (`bv-service-*`) | 51 | — |
| testimonials + `BV_TESTIMONIALS` | 38 | — |
| logo-first cards (`BV_CARD_LOGOS`, `bv-card--logo`) | 13 | — |
| work filter and search (`bv-filter-bar`, `workStatus`) | 13 | — |
| Shalaby Labs case file | 18 | — |

Measured, not assumed: a `build-embed.mjs` run from today's `site/` produces
**536,598 bytes**, the size of the committed pre-redesign page. The working file
is **727,764**. Running that build today deletes five shipped features.

The media refresh ends in `gen-media-map.mjs` → `build-embed.mjs`. So either the
port happens first, or several hundred media entries get hand-written into a
generated file the project rules forbid hand-editing.

**Decided:** port the five features into `site/`, verify by rebuilding, then run
everything else through the existing pipeline. Two alternatives were considered
and rejected: retiring `site/` and rewriting the ten tools that read from it
(`build-embed`, `gen-media-map`, `stage-upload`, and `map`, `mobile`, `squeeze`,
`profile`, `video`, `ingest-reels`, `shrink-reels` under `tools/`) — more work,
same destination; and hand-wiring the media into the embed, which defers the
same port and makes it larger.

One piece of luck makes this cheaper than it looks: `BV_MEDIA` is **572 entries
in the embed against 574 generated**. The media map has not meaningfully
diverged, so `gen-media-map.mjs` output drops straight in.

## Part 1 — The port

Each feature moves into the module that already holds its kind, matching where
the embed itself carries the code:

- services section → `site/css/beeviro.css` + `site/js/beeviro.js`
- testimonials → `BV_TESTIMONIALS` data and builder in `site/js/beeviro.js`,
  styles in `beeviro.css`, five new keys in `site/js/i18n.js`
- `BV_CARD_LOGOS` and the adaptive logo grading → data and grading in
  `site/js/beeviro.js`, cell rendering in `site/js/hive.js`, the
  `cover`/`contain` switch in `beeviro.css`
- work filter and search → `site/js/beeviro.js`, beside the grid it filters
- Shalaby Labs → a record in `site/js/clients.js` and `clients.ar.js`, plus its
  ten `BV_MEDIA` lines

**No new modules.** `build-embed.mjs:127` inlines a hardcoded list of nine, and
`site/index.html` names the same nine in the same order; adding files means
editing both and taking on a load-order risk for globals like
`BV_TESTIMONIALS`. Since the acceptance criterion is *no functional delta*,
minimising structural change is what makes the diff meaningful — restructuring
during a port conflates two risks. `beeviro.js` is 79KB and will grow; splitting
it is worth doing, but as its own change against a green baseline, not here.

Three smaller pieces of this session's work ride along in the same files: the
embedded Cairo face and the `[dir="rtl"]` font-variable redefinition, the mobile
hero rebalance, and the language-toggle reload fix.

**Success criterion.** Rebuild from `site/` and compare against today's embed.
The target is not byte-identity — the generator reorders things — but no
functional delta: same feature count, same `BV_MEDIA` entries, same rendered
page in both languages at desktop and mobile widths, driven in a browser rather
than checked by eye.

### What COLLAGE means

The word appears eight times and is load-bearing. Confirmed with the client:
**composite images, built here**, and the rule for what gets combined is theirs:

> similar pictures go into a collage; different ones are placed separately

That is a clustering problem, not a judgement call. Perceptual-hash every image
in a client's folder, group by Hamming distance, composite each cluster of two
or more into a single tile, leave singletons alone. It answers the repetition
complaint identically across all fourteen clients. For CogniStar the client
named the cluster explicitly — the teacher posts.

### Pipeline

Steps 1–4 are new. Steps 5–8 exist and have absorbed 196- and 378-file batches.

1. **Enumerate** — open each folder in a browser, scroll to defeat Drive's row
   virtualization, recurse into subfolders (`CAROUSEL`, `CAROUSEL 2`), and emit
   a manifest of id, name, size and type. Folder titles confirm the mapping
   above before anything downloads.
2. **Fetch** — `https://drive.google.com/uc?export=download&id=…`, anonymous.
   Verified: the folders are world-readable and a sample file returned 770,549
   bytes of valid JPEG without a session.
3. **Cluster** — perceptual hash per client, group by distance threshold.
   Implemented in plain Node; no dependency is added.
4. **Composite** — draw each cluster to a canvas in Chromium and export. This is
   how `squeeze.mjs` and `make-thumbs.mjs` already do image work, so it adds no
   dependency and the no-build rule holds.
5. **Optimize** — existing `make-thumbs.mjs` (480px and 200px tiers) and
   `squeeze.mjs`. Video through `ingest-reels.mjs` / `shrink-reels.mjs`.
6. **Stage** — `stage-upload.mjs`, which flattens `site/assets` into
   `upload-staging/` under names unique enough for a library that discards
   folder paths, and writes the site-path → upload-name manifest that
   `gen-media-map.mjs` consumes. See the incremental-upload risk below: it
   rebuilds the directory wholesale.
7. **Upload** — manual, by the operator. The media library sits behind a
   GoHighLevel login that nothing here can reach. Then
   `tools/harvest-media-ids.js` is pasted into the browser console to produce
   `bv-media-ids.json`.
8. **Map and wire** — `gen-media-map.mjs` → `site/js/media-map.js`, then per
   client `work:` counts, then `build-embed.mjs`.

### Decisions on placement

**Replacement, not addition.** For the fourteen clients with new material, the
new pieces replace what their cards show today. The brief reads as replacement
throughout — *"don't put the gallery images"* (Moafa), *"the designs aren't the
best thing"* (MasterCraft). Superseded pieces stay on disk and stay in
`BV_MEDIA`; they simply stop being referenced by a client record.

**Video lands in three places.** Each client's strongest cut replaces their
case-file `film:`. The remainder become playable tiles in the case gallery. The
new reels also widen the hero comb, which drops to twelve entries after the
removals — restoring and extending the pool the client complained about in the
previous review round.

**Raw downloads stay out of git.** `sources/` and `upload-staging/` are tracked
today at 227MB and 42MB. The Drive folders hold files up to 12MB and are
expected to add 0.8–3GB. `sources/drive/` is added to `.gitignore`; only
processed, optimized output is committed. Re-running the fetch is cheap; a
multi-gigabyte history is permanent.

## Constraints

Inherited by every task.

- **REDACTION RULE.** Nothing published may carry competitor names or teardowns,
  internal media budgets, unpublished projections, phone numbers or personal
  handles. `sources/` must never ship.
- **EDITORIAL RULE.** `outcome.kind: 'result'` only where the figure appears in
  the client-approved document. Never promote a `goal` to a `result` without a
  source. Never add a metric without a `note`.
- Site JavaScript is **plain ES2019**: `var`, `function`, no arrow functions, no
  `const`/`let`, no template literals, no optional chaining, and it must run
  from `file://`. Tooling under `tools/` and at the repo root is modern Node ESM
  and carries no such limit.
- **No dependencies and no build step.** There is no `package.json` and none is
  to be added. Image work goes through Chromium, as the existing tools do.
- `site/` is the only deployable root.
- Never hand-edit `beeviro-embed.html`, `split/*`, `site/js/media-map.js` or
  `site/js/thumb-map.js` — all four are generated. **After Part 1 this rule
  becomes enforceable again**, which is most of why Part 1 exists.
- Anchor every edit on unique surrounding text, never on line numbers.
- Shalaby Labs' own website is theirs, not work done here; it must not be linked
  or presented as ours.

## Risks and open items

- **The port is the risky step.** Five working features move between files. It is
  mitigated by the rebuild-and-compare criterion in Part 1, and by the fact that
  today's embed is a known-good reference to diff against — but nothing else in
  this spec can start until it lands.
- **Drive access is unauthenticated and could change.** The folders are
  world-readable today. If sharing is tightened mid-run, enumeration and fetch
  both stop. Fetch early; keep the raw files until the work ships.
- **Upload volume.** Several hundred files through a manual bulk upload. The
  pipeline has done 378 in one pass before, so this is known rather than novel,
  but it is the one step nothing here can automate.
- **Staging is all-or-nothing.** `stage-upload.mjs` opens with an `rmSync` on
  `upload-staging/` and re-flattens every shipped asset, currently 585 files.
  Uploading that wholesale would duplicate everything already in the library,
  since GoHighLevel mints a new id per upload and the existing map would still
  point at the old ones. The plan needs an incremental path — diff the new
  manifest against the harvested ids and stage only what is genuinely new —
  before step 7 is safe to run. This is the sharpest operational risk in Part 3.
- **Tamahwour and Edara Plus have notes but no assets.** Logged so the gap is not
  mistaken for an oversight later.
- **`revenuelab360` and `tamahwour` have no card logo.** Their cards keep using
  gallery art.
- **Clustering threshold needs calibration.** Too tight and near-duplicates stay
  separate; too loose and unrelated designs get composited together. Calibrate
  against one client — CogniStar, where the intended cluster is named — before
  running the other thirteen.
